파일명에 최종, 진짜최종을 붙여 본 경험을 먼저 물어보세요. Git은 파일을 여러 개 만드는 대신 한 파일의 변화 기록을 쌓아 둬요. 그 기록 하나가 커밋이고, 앞의 7자리는 커밋마다 붙는 고유 번호(해시)예요. 원하는 시점으로 언제든 돌아갈 수 있어요.

빨간 글씨는 대기실 밖, 초록 글씨는 대기실 안이에요.

Untracked와 Modified는 둘 다 빨간색이지만 달라요. Untracked는 Git이 처음 보는 파일, Modified는 이미 아는 파일이 바뀐 거예요. 둘 다 git add로 대기실에 올려요. 한 번이라도 커밋된 파일을 Tracked(추적 중)라고 불러요.

새 파일은 Untracked로 시작해요. add 하면 Staged, commit 하면 Committed. 책에 따라 Committed를 Unmodified라고 부르기도 하지만, git status에는 어느 단어도 나오지 않고 working tree clean으로만 보여요. 그 뒤로 파일을 고치면 Modified가 되고 다시 add, commit을 반복해요. 이 고리가 Git 작업의 기본 리듬이에요.

실습 0 · 컴퓨터마다 처음 한 번만

Git에게 내 이름을 알려 줘요

$ git config --global user.name "홍길동"

$ git config --global user.email "gildong@example.com"

$ git config --global init.defaultBranch main

 

$ git config --global --list

user.name=홍길동

user.email=gildong@example.com

init.defaultbranch=main

← 커밋마다 붙는 작성자 이름

← GitHub 가입 메일과 같게

← 기본 브랜치 이름을 main으로

--global은 이 컴퓨터 전체에 적용돼요. 그래서 한 번만 하면 돼요.

설정은 컴퓨터마다 한 번만 하면 돼요. 안 하면 첫 커밋 때 "Author identity unknown *** Please tell me who you are." 에러가 나요. init.defaultBranch main을 해 두면 git init으로 만든 저장소의 브랜치 이름이 GitHub과 같은 main이 돼요. GitHub의 main 기본값은 GitHub에서 만든 저장소에만 적용돼요. 이 설정이 없으면 git init이 master 브랜치를 만들 수 있고, 그러면 git push origin main에서 "src refspec main does not match any" 에러가 나요.

방금 두 번 커밋하면서 메시지 앞에 feat: 를 붙였죠. 그게 무슨 뜻인지 여기서 짚고 넘어가요. 오른쪽에서 동그라미 친 칸이 타입이에요. 커밋 메시지는 미래의 나와 팀원에게 남기는 송장이에요. 버그가 생겼을 때 fix 커밋만 훑어보거나, 어떤 기능이 언제 들어왔는지 feat 커밋으로 바로 찾을 수 있어요.

GitHub과 비교는 log로 해요

git fetch origin → git log --oneline origin/main

main이 위 → git push origin main

origin/main이 위 → git pull origin main

우리 과정은 -u를 쓰지 않아서 git status가 GitHub과 비교한 결과(ahead, behind)를 보여주지 않아요. 그래서 마지막 줄이 clean이어도 push를 안 했을 수 있어요. GitHub과의 차이는 fetch한 뒤 git log --oneline에서 main과 origin/main 이름표 위치로 확인해요.

에러 1 · index.lock

index.lock은 Git의 ‘사용 중’ 팻말이에요

팻말 걸기

작업 중

명령 끝

팻말 떼기

끝나기 전에 멈추면 팻말이 남아요

터미널 창을 강제로 닫았을 때

커밋 메시지 에디터를 닫지 않았을 때

VS Code가 같은 저장소에서 git을 실행 중일 때

index는 대기실의 정식 이름이에요. add, commit, pull처럼 대기실을 고치는 명령이 일하는 동안 다른 명령이 끼어들지 못하게 Git이 스스로 잠가 둬요. 정상이라면 명령이 끝날 때 저절로 사라지고, 비정상 종료됐을 때만 남아서 에러를 내요.

에러 1 · index.lock

이 메시지가 보이면 팻말만 떼요

$ git add hello.md

fatal: Unable to create '/Users/kim/hello-git/.git/index.lock': File exists.

Another git process seems to be running in this repository, ...

1

다른 git 작업이 끝났는지 봐요

커밋 에디터, 다른 터미널 창, VS Code

2

팻말을 떼요

rm .git/index.lock

3

아까 명령을 다시 쳐요

git add hello.md

Mac 터미널, Windows Git Bash 똑같아요

지우는 건 index.lock 하나뿐이에요. index나 .git 폴더는 지우지 않아요.

1번은 열려 있는 커밋 에디터, 다른 터미널 창, VS Code의 Git 작업을 확인하는 단계예요. 이걸 건너뛰고 지우면 실제로 돌던 작업과 부딪힐 수 있어요. 명령은 .git 폴더가 있는 저장소 맨 위에서 쳐요. 우리 과정은 Windows에서도 Git Bash를 쓰니 rm 명령이 똑같이 돼요. 메시지 원문 뒷부분은 "다른 git이 실행 중인 것 같다, 예전에 비정상 종료됐다면 파일을 직접 지워라"라는 뜻이에요.

에러가 --set-upstream(-u)을 권해도 쓰지 않아요

-u로 짝을 지어 두지 않았기 때문에 git push, git pull만 치면 Git이 어디로 보낼지 몰라서 멈춰요. 우리 과정에서는 -u를 쓰지 않기로 했으니, 에러 메시지가 git push --set-upstream origin main을 권해도 따르지 말고 git push origin main처럼 끝까지 적어요.

--force는 쓰지 않아요

Git은 팀원의 커밋을 지우지 않으려고 push를 막아요. 먼저 받아서 합친 뒤 다시 보내면 돼요. GitHub에서 README를 체크해 저장소를 만들었거나 웹에서 파일을 고친 경우 혼자 작업해도 이 에러가 나요. --force는 팀원 커밋을 지워 버려요. hint 줄은 앞부분만 옮겼어요.

에러 5 · push 거절

pull 설정을 한 번 해 두고 받아서 합쳐요

$ git pull origin main

From https://github.com/kim/hello-git

 * branch main -> FETCH_HEAD

hint: You have divergent branches and need to specify how to reconcile them.

fatal: Need to specify how to reconcile divergent branches.

$ git config --global pull.rebase false

$ git pull origin main

Merge made by the 'ort' strategy.

 README.md | 1 +

$ git push origin main

   dac2ff4..71f86b2 main -> main

← 처음 한 번만 쳐요 (03에서 다시 봐요)

← vim이 열리면 :wq 치고 Enter

pull.rebase 설정이 없으면 내 main과 GitHub main이 갈라졌을 때 Git이 어떻게 합칠지 물으면서 fatal로 멈춰요. 멈춘 pull은 커밋도 파일도 바꾸지 않아요. hint 첫 줄에 나온 pull.rebase false가 우리가 고르는 merge예요. --global을 붙여 한 번 설정하고 같은 pull을 다시 치면 두 커밋이 합쳐진 merge 커밋이 생겨요. 이때 커밋 메시지를 적는 vim이 열리면 그대로 :wq, Enter로 닫아요. 합친 뒤에는 push가 돼요. merge 커밋 모양은 03에서 자세히 봐요. hint 줄은 앞부분만 옮겼고, 해시는 사람마다 달라요.
