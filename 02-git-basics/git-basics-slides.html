파일은 하나, 기록은 여러 개

파일명에 최종, 진짜최종을 붙여 본 경험을 먼저 물어보세요. Git은 파일을 여러 개 만드는 대신 한 파일의 변화 기록을 쌓아 둬요. 그 기록 하나가 커밋이고, 앞의 7자리는 커밋마다 붙는 고유 번호(해시)예요. 원하는 시점으로 언제든 돌아갈 수 있어요.

커밋 메시지 = 송장 · 커밋 해시 = 운송장 번호

담기(add)와 봉하기(commit)를 나누는 이유는, 여러 파일을 고쳤어도 이번 기록에 넣을 것만 골라 담을 수 있게 하려는 거예요.

용어 ① 파일의 상태

상태뜻git status에 보이는 말
Untracked처음 보는 새 파일Untracked files:
Modified고쳤지만 add 전Changes not staged for commit:
Staged대기실에 올라감Changes to be committed:
Committed마지막 커밋과 같음working tree clean

빨간 글씨 = 대기실 밖

초록 글씨 = 대기실 안

Untracked와 Modified는 둘 다 빨간색이지만 달라요. Untracked는 Git이 처음 보는 파일, Modified는 이미 아는 파일이 바뀐 것. 둘 다 git add로 대기실에 올려요. 한 번이라도 커밋된 파일을 Tracked(추적 중)라고 불러요.

용어 ② 저장소와 이름표

용어한 줄 뜻
Repository커밋 기록 보관함 (.git, GitHub)
Index대기실의 정식 이름
Commit · 해시저장된 한 시점과 그 고유 번호
branch (브랜치)커밋에 붙이는 이름표. 03에서 자세히 봐요
main기본 브랜치. 최신 커밋에 붙은 이름표
HEAD내가 지금 서 있는 곳
originGitHub 주소의 별명
origin/main내 컴퓨터가 기억하는 GitHub main 위치
origin은 명령어가 아니라 주소의 별명이에요. origin/main은 마지막으로 push하거나 fetch한 시점의 GitHub 모습이라, 최신 상태를 보려면 git fetch origin으로 다시 확인해요. index는 뒤에서 나올 index.lock 에러의 그 index예요.

파일 수정

새 파일은 Untracked로 시작해요. add 하면 Staged, commit 하면 Committed. 책에 따라 Committed를 Unmodified라고 부르기도 하지만, git status에는 어느 단어도 나오지 않고 working tree clean으로만 보여요. 그 뒤로 파일을 고치면 Modified가 되고 다시 add, commit을 반복해요. 이 고리가 Git 작업의 기본 리듬이에요.

실습 0 · 컴퓨터마다 처음 한 번만

Git에게 내 이름 알려주기

$ git config --global user.name "홍길동"

$ git config --global user.email "gildong@example.com"

$ git config --global init.defaultBranch main

 

$ git config --global --list

user.name=홍길동

user.email=gildong@example.com

init.defaultbranch=main

커밋마다 붙는
작성자 이름

이메일은
GitHub 가입 메일과 같게

기본 브랜치 이름을
main으로

설정은 컴퓨터마다 한 번만 하면 돼요. 안 하면 첫 커밋 때 "Author identity unknown *** Please tell me who you are." 에러가 나요. --global은 이 컴퓨터 전체에 적용한다는 뜻. init.defaultBranch main을 해 두면 git init으로 만든 저장소의 브랜치 이름이 GitHub과 같은 main이 돼요. GitHub의 main 기본값은 GitHub에서 만든 저장소에만 적용돼요. 이 설정이 없으면 git init이 master 브랜치를 만들 수 있고, 그러면 git push origin main에서 "src refspec main does not match any" 에러가 나요.

① + ② 한 번에

pull을 두 단계로 나눠 보여주세요. fetch는 GitHub 소식을 받아 origin/main만 옮기고 내 파일은 건드리지 않아요. merge가 그걸 내 main과 작업 폴더에 합쳐요. 여기서는 "받아서 합친다"까지만 기억하면 돼요. merge가 어떻게 합치는지, 충돌(CONFLICT)이 나면 어떻게 푸는지는 03 브랜치 자료에서 봐요.

GitHub과 비교는 log로

git fetch origin → git log --oneline origin/main

main이 위 → push origin main

origin/main이 위 → pull origin main

우리 과정은 -u를 쓰지 않아서 git status가 GitHub과 비교한 결과(ahead, behind)를 보여주지 않아요. 그래서 마지막 줄이 clean이어도 push를 안 했을 수 있어요. GitHub과의 차이는 fetch한 뒤 git log --oneline에서 main과 origin/main 이름표 위치로 확인해요.

index는 대기실의 정식 이름이에요. add, commit, pull처럼 대기실을 고치는 명령이 일하는 동안 다른 명령이 끼어들지 못하게 Git이 스스로 잠가 둬요. 정상이라면 명령이 끝날 때 저절로 사라지고, 비정상 종료됐을 때만 남아서 에러를 내요.

이 메시지가 보이면

$ git add hello.md

지우는 건 index.lock 하나만. index나 .git 폴더는 절대 지우지 않아요.

1번은 열려 있는 커밋 에디터, 다른 터미널 창, VS Code의 Git 작업을 확인하는 단계예요. 이걸 건너뛰고 지우면 실제로 돌던 작업과 부딪힐 수 있어요. 명령은 .git 폴더가 있는 저장소 맨 위에서 실행해요. 메시지 원문 뒷부분은 "다른 git이 실행 중인 것 같다, 예전에 비정상 종료됐다면 파일을 직접 지워라"라는 뜻이에요.

에러 2 · add 없이 commit

commit 했는데 아무 일도 없어요

$ git commit -m "feat: 새 파일"

Untracked files:

        new.md

files present

 

$ git commit -m "fix: 오타 수정"

Changes not staged for commit:

        modified:   hello.md

no changes added to commit

② 대기실이 비어 있어요

git add 파일

git commit -m "..."

commit은 대기실에 있는 것만 기록해요. 빨간 글씨가 보이면 아직 대기실 밖이라는 뜻이니 add부터. 출력 끝의 (use "git add" to track) 같은 안내 문구는 화면 폭 때문에 줄였어요.

에러 3 · origin 설정

origin이 이미 있대요, 혹은 없대요

두 번 등록함

error: remote origin already exists.

git remote -v

git remote set-url origin 새주소

등록 안 함

fatal: 'origin' does not appear to be a git repository

git remote add origin 주소

git push origin main

이미 있다는 에러는 remote add를 두 번 했거나 clone 받은 저장소에서 또 등록하려 할 때 나요. 주소를 잘못 넣었으면 set-url로 고쳐요. 없다는 에러는 init으로 시작해 놓고 remote add를 빠뜨렸을 때 나요. 어느 쪽이든 git remote -v로 지금 등록된 걸 먼저 확인하세요.

에러 4 · 어디로 보낼지 안 적음

git push만 쳤더니 거절돼요

$ git push

fatal: The current branch main has no upstream branch.

$ git pull

There is no tracking information for the current branch.

우리 과정 규칙: 어디로, 무엇을 항상 적기

git push

origin

main

git pull

origin

main

--set-upstream(-u) 안내가 떠도 쓰지 않아요

-u로 짝을 지어 두지 않았기 때문에 git push, git pull만 치면 Git이 어디로 보낼지 몰라서 멈춰요. 우리 과정에서는 -u를 쓰지 않기로 했으니, 에러 메시지가 git push --set-upstream origin main을 권해도 따르지 말고 git push origin main처럼 끝까지 적어요.

팀원 커밋

서로 모르는 커밋이 생겼어요

1. git pull origin main

2. git push origin main

--force는 쓰지 않아요

Git은 팀원의 커밋을 지우지 않으려고 push를 막아요. 먼저 받아서 합친 뒤 다시 보내면 돼요. GitHub에서 README를 체크해 저장소를 만들었거나 웹에서 파일을 고친 경우 혼자 작업해도 이 에러가 나요. pull 하다 충돌(CONFLICT)이 나면 03 브랜치 자료의 충돌 풀기를 봐요. --force는 팀원 커밋을 지워 버려요.
